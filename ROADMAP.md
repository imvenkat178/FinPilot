# FinPilot roadmap

> The long-term goal tree for FinPilot, shared by every human and AI agent working on this repository.
> [HANDOFF.md](HANDOFF.md) records the latest session and the current focus. This file records where the product is going.
> Protocol: [AGENTS.md](AGENTS.md). Commands: `python scripts/roadmap.py next | status | write | check | json`.

## How this file works

**Levels.** A goal (`G1`) is a lasting outcome. A sub-goal (`G1.1`) is a verifiable result inside it. A task (`G1.1.1`) is roughly one session of work.

**Horizon** is set on every sub-goal. Rewrite the meanings to fit this project, but keep the three tags:

| Tag | Meaning |
| --- | --- |
| `short-term` | Needed before real users rely on FinPilot (launch blockers and launch hardening) |
| `mid-term` | Expected in the first months after launch |
| `long-term` | Growth, scale and product decisions |

**Priority** within a horizon: `P0` critical, `P1` high, `P2` normal, `P3` low.

**Status:** `todo`, `doing`, `blocked` (add a `Blocked by:` line), `decision` (add a `Decision needed:` line; only the user decides), `done`, `dropped` (keep the entry and explain why).

**Sub-goal format.** The validator depends on it:

```
### G1.1 Short title
`short-term` `P0` `todo` needs: G2.1
Why: the problem, with evidence.
Evidence: how it was verified, and how strongly.
Done when: the observable result.
- [ ] G1.1.1 A concrete task.
- [x] G1.1.2 A finished task. (done 2026-01-01: the proof, such as a commit, test or file)
```

Optional lines: `From:` names an outside suggestion that was merged in. `Adapted from:` means the suggestion was changed to fit this project, with the reason.

**Rules for every agent**

1. Never renumber or reuse an ID. New entries take the next free number in their parent.
2. Never delete an entry. Set `dropped` and say why.
3. Check a task only with evidence in a `(done YYYY-MM-DD: ...)` note.
4. Update the sub-goal status in the same edit: `doing` when work starts, `done` when every task is checked and the "Done when" result is true.
5. Record newly discovered work here as tasks or sub-goals instead of leaving it in chat.
6. Never move a `decision` sub-goal forward without the user's answer.
7. Before finishing, run `scripts/roadmap.py write`, then `scripts/check_handoff.py --strict`, and log the session in `HANDOFF.md`.

## G1. Security and privacy

Outcome: financial data stays private in logs, networks, model calls and storage, and the application resists common web attacks.

### G1.1 Privacy-safe request logging
`short-term` `P0` `todo`
Why: under default uvicorn logging, the privacy-filtered `finpilot.requests` line in `finpilot/api/app.py` is never emitted, while the uvicorn access log prints full query strings such as `GET /api/transactions?q=therapy-copay&category=medical` and amounts such as `/api/debt/what-if?amount=`. Reverse proxies often log query strings too.
Evidence: verified 2026-09-13 by running the app locally with uvicorn 0.52.4 defaults. This contradicts the logging statement in `ARCHITECTURE.md`.
Done when: a production-configured deployment writes one privacy-safe line per request, and no query string, body or amount appears in application, server or proxy logs.
- [ ] G1.1.1 Configure the `finpilot` logger at startup so the request line is emitted under uvicorn.
- [ ] G1.1.2 Keep query strings out of server logs: run uvicorn with `--no-access-log` in the `Dockerfile`, or install an access-log filter that drops query strings.
- [ ] G1.1.3 Move amount-bearing reads (`/api/debt/what-if`, `/api/tax/net-benefit`, mortgage scenarios) to request bodies, or document a proxy log format without query strings.
- [ ] G1.1.4 Add a regression test that captures logs for a request with a sensitive query string and asserts nothing sensitive is written.
- [ ] G1.1.5 Update the logging statement in `ARCHITECTURE.md` once behaviour matches.

### G1.2 Correct client addresses behind a proxy
`short-term` `P0` `todo`
Why: uvicorn trusts `X-Forwarded-For` only from `127.0.0.1` unless `FORWARDED_ALLOW_IPS` is set, and neither the `Dockerfile` nor `compose.yaml` sets it. Behind a proxy every user shares one address, so the IP-keyed sign-up limit (8 per 5 minutes) and sign-in limit (30 per 5 minutes) apply to all users together.
Evidence: read from uvicorn 0.52.4 defaults and the missing setting on 2026-09-13. Not yet reproduced behind a real proxy.
Done when: behind the production ingress, throttles key on the real client address, and forwarding headers from untrusted peers are ignored.
- [ ] G1.2.1 Reproduce the shared-address lockout behind a local reverse proxy container.
- [ ] G1.2.2 Set `FORWARDED_ALLOW_IPS` to the ingress address in the `Dockerfile`, `compose.yaml` and `DEPLOYMENT.md`.
- [ ] G1.2.3 Add a test that throttle keys use the forwarded address only for trusted peers.

### G1.3 Strict Content-Security-Policy
`mid-term` `P1` `todo`
Why: the current policy only sets `frame-ancestors`, `base-uri` and `object-src`, so it does not restrict scripts.
Evidence: checked `finpilot/api/app.py` and `finpilot/web/` on 2026-09-13. The frontend has no inline scripts or inline event handlers. External origins are the Plaid CDN and Google Fonts, and `core.js` and `pages.js` contain inline `style=` attributes.
Done when: a strict policy is enforced in production with no violations across the main journeys.
- [ ] G1.3.1 Add `default-src 'self'` with explicit script, style, font, connect and frame sources for Plaid and Google Fonts.
- [ ] G1.3.2 Replace inline `style=` attributes with CSS classes.
- [ ] G1.3.3 Ship as `Content-Security-Policy-Report-Only` first, then enforce.
- [ ] G1.3.4 Consider self-hosting fonts so no third party receives user IP addresses.

### G1.4 Keep personal data out of external model calls
`short-term` `P1` `todo` needs: G7.2
Adapted from: "zero-knowledge architecture and PII redaction". Full zero-knowledge is not possible because the server must read financial data to calculate. The adapted goal is data minimization for anything sent to a model provider or tracing service.
Why: if the production model is a third-party API, prompts can carry names, institutions, account nicknames, amounts and document text.
Evidence: `finpilot/ai/input_safety.py` rejects credential-like input (passwords, API keys, tokens, private keys) before prompts and storage. Nothing masks account numbers, card numbers or SSNs. LangSmith tracing is opt-in through `LANGCHAIN_TRACING_V2` in `finpilot/ai/graph.py` and would send traces to a third party. Checked 2026-09-13.
Done when: prompts and traces sent outside the deployment contain only the fields they need, identifiers are masked, and each provider's data terms are documented.
- [ ] G1.4.1 Inventory every prompt builder (planner context, explanations, knowledge extraction) and the personal fields each sends.
- [ ] G1.4.2 Mask account, routing and card numbers and SSN patterns before external calls, with tests.
- [ ] G1.4.3 Prefer providers with zero-retention or no-training terms and record them in `DEPLOYMENT.md`.
- [ ] G1.4.4 Block LangSmith tracing in production unless redaction is in place.

Evidence: Fernet usage in `finpilot/integrations/plaid.py` and `finpilot/integrations/mcp_client.py`.
Done when: managed PostgreSQL and backups are encrypted at rest, ingress allows only TLS 1.2 or newer with 1.3 preferred, and the posture is documented.
- [ ] G1.6.1 Confirm encryption at rest for the chosen managed PostgreSQL and its backups.
- [ ] G1.6.2 Configure the ingress TLS policy and verify it with an external TLS scanner.
- [ ] G1.6.3 Move stored credentials to AES-256-GCM only if a chosen compliance framework requires it.

`short-term` `P1` `todo` needs: G4.1
Why: FinPilot will hold bank tokens and financial history, and no external review has taken place.
Done when: a penetration test of the hosted staging environment is complete and every high-severity finding is fixed.
- [ ] G1.7.1 Run an automated web scan (for example OWASP ZAP) against staging.

### G1.8 Database row-level security
`long-term` `P2` `todo`
Adapted from: "row-level security in PostgreSQL". Tenant isolation already exists in application code, so this is defense in depth rather than a migration.
Why: a future query that forgets its household filter would currently rely on tests alone to be caught.
Evidence: the household is derived from the session on every route, and cross-tenant denial tests pass (`END_TO_END_VALIDATION.md`).
Done when: PostgreSQL policies block cross-household reads even when an application query omits its filter.
- [ ] G1.8.1 Design a per-transaction household setting compatible with the session-per-operation runtime.
- [ ] G1.8.2 Add policies through an Alembic migration and prove them with a test that omits a filter.

## Considered and not adopted

These suggestions came from a production-readiness list the user supplied on 2026-09-13. They conflict with deliberate FinPilot design decisions or do not apply. Revisit one only with a new reason, and record the change in `HANDOFF.md` section 7.

- **Replace server-side sessions with JWTs and refresh-token rotation.** Opaque session tokens are hashed at rest and revoke immediately; client-held JWTs make revocation harder. Hosted identity or OIDC sign-in stays possible through G2.9.
- **Zero-knowledge architecture.** The server must read financial data to calculate plans. Adapted into data minimization for external calls (G1.4).
- **Semantic caching of answers in Redis.** Answers depend on live household data and revisions, and similarity-based caching risks stale or cross-household results. Existing caches are keyed by household revision. Revisit only for public market data (G12.3).
- **Streaming raw model tokens as the answer.** Unverified numbers would reach the screen before grounding checks. Adapted into progress-stage streaming (G7.8).
- **Adding NeMo Guardrails or Instructor.** Typed planner schemas, server validation and numeric grounding already cover this (G7.1). Revisit if AI evaluations show guard gaps (G5.7).
- **Moving off SQLite, JSON files and in-memory vector stores.** Production already requires PostgreSQL, and there is no vector store. Semantic search is planned on PostgreSQL (G10.2).
- **Replacing CSV and PDF import with aggregation only.** Manual import stays as the fallback for unsupported institutions and privacy-minded users, alongside G8.
